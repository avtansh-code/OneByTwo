PHASE 3 — ARCHITECT NOTES
────────────────────────────────────────

Owner: architect.

Append `## Architect Notes` to the story covering:

3.1  Function shape:
     - Name: `recomputeSimplifiedBalances`.
     - Region: `asia-south1` (hard-coded; the prompt's PreToolUse hook will reject any other region).
     - Trigger: HTTPS callable for this PR. Auth context required (server-side service-account-only invocation when later wired as a Firestore trigger).
     - Input contract: `{ contextType: 'friendship' | 'group', contextId: string }`.
     - Output contract: `{ ok: true, transfers: Array<{ fromUserId: string, toUserId: string, amountPaise: number }>, simplifiedBalances: <nested map matching firestore-schema.md>, computedAt: ISO timestamp }` on success; typed error envelope on failure.

3.2  Idempotency:
     - The function is naturally idempotent: it reads the current expense + settlement log for the context and writes the derived `simplifiedBalances`. Re-running with the same inputs and the same source-of-truth state produces the same output and the same write.
     - However, the function MUST run inside a Firestore transaction that reads the expenses and settlements AND writes `simplifiedBalances` atomically, so two concurrent invocations cannot interleave a write.

3.3  Error model:
     - A typed error union: `INVALID_INPUT`, `CONTEXT_NOT_FOUND`, `PERMISSION_DENIED`, `INTERNAL`.
     - Generic `Error` is never thrown to the caller. All caught exceptions are mapped to one of the typed errors at the function boundary.
     - The error model is documented in a new file `docs/design/07-technical/cloud-functions-error-codes.md` (architect deliverable, modelled on `auth-error-codes.md` from PR #7). This pattern propagates to every future Cloud Function.

3.4  Logging:
     - Use `firebase-functions/logger` (or the chosen structured logger) for every event.
     - Structured fields: `event`, `contextType`, `contextId`, `elapsedMs`, `errorCode` (when applicable). NEVER log `userId` values, raw amounts, or any PII per SRS §5.4.

3.5  Determinism:
     - Per the algorithm spec, ties between creditors or debtors break by ascending `userId`. The unit tests verify this is consistent across invocations. Document this rule in a comment at the top of the algorithm module so any future maintainer sees it without hunting.

3.6  Performance budget:
     - SRS §5.2: ≤500 ms P95 for groups up to 50 members.
     - The function logs `elapsedMs` on every invocation. After deploy, the architect verifies a synthetic invocation with a mock 50-member group hits the budget. Record the result in the PR body.

PHASE 4 — TEST-FIRST DISCIPLINE
────────────────────────────────────────

Tests are written before implementation, in this order. This is THE pattern-setter for Cloud Function tests — every future function copies this layout.

1. Algorithm unit tests (`functions/test/simplified-debts/algorithm.test.ts`):
   The six canonical cases from the algorithm spec, each as a discrete test with clearly-named inputs and expected outputs:
     - `empty input returns empty transfers`
     - `single member with no expenses returns empty transfers`
     - `perfectly balanced two-member group returns empty transfers`
     - `three-person trip with cyclic debts simplifies to two transfers`
     - `three-person canonical case from spec`
     - `five-person flat-share canonical case from spec`
   Each test asserts:
     - The transfer count matches the spec.
     - Every transfer's `amountPaise` is a non-negative integer.
     - The sum of all `amountPaise` equals the spec's expected total.
     - The tie-break rule (ascending userId) is respected — write a test specifically with tied creditors AND tied debtors to verify deterministic ordering.

2. Algorithm property tests (`functions/test/simplified-debts/algorithm.property.test.ts`) — at least three properties:
   - For any valid input, transfer count ≤ N − 1 where N is the member count (the algorithm never produces redundant transfers).
   - For any valid input, applying all transfers to the input balances yields zero net for every member.
   - The function is deterministic: invoking twice with the same input produces identical output.

3. Function-boundary tests (`functions/test/simplified-debts/function.test.ts`) using `firebase-functions-test`:
   - Valid input returns the expected output shape.
   - Missing `contextId` returns `INVALID_INPUT` (typed error, not generic Error).
   - Unknown `contextType` returns `INVALID_INPUT`.
   - Non-existent context returns `CONTEXT_NOT_FOUND`.
   - Successful invocation logs `simplified_debts_compute_started` and `simplified_debts_compute_completed`.
   - Failed invocation logs `simplified_debts_compute_failed` with the error code, no PII.

4. Firestore Security Rules tests (`functions/test/firestore-rules/simplified-balances.test.ts`):
   - Authenticated client CAN read `simplifiedBalances` on a friendship they belong to.
   - Authenticated client CAN read `simplifiedBalances` on a group they belong to.
   - Authenticated client CANNOT write `simplifiedBalances` on any document — verify with at least three negative cases (own friendship, own group, malicious cross-write attempt).
   - Unauthenticated client CANNOT read `simplifiedBalances`.
   - Cloud Functions service account CAN write `simplifiedBalances` (verify with the rules-unit-testing emulator's admin context).

5. Integration test against the emulator (`functions/test/integration/simplified-debts.integration.test.ts`):
   - Seed a friendship with two members and three expenses with known splits in the emulator.
   - Invoke `recomputeSimplifiedBalances` via the callable interface.
   - Assert the resulting `simplifiedBalances` matches the canonical case.
   - Variant: seed a group with five members and the canonical five-person case; invoke; assert.
   - Variant: invoke twice in succession; assert idempotent (no duplicate writes, no drift).
   - Negative variant: invoke as an unauthenticated caller; assert PERMISSION_DENIED.

6. ONLY after all five test files are red, functions-dev implements the algorithm and the function boundary.

Coverage on `functions/src/simplified-debts/**` must be 100% branch coverage of the canonical test matrix per DoD §2 (the patterns document elevates simplified-debts coverage above the general 70% threshold for this reason). Functions-dev confirms branch coverage in the PR body.
