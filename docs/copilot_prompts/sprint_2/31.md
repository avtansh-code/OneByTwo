## 1. Scope — what we build

**A defence-in-depth Firestore-rules tightening: only the expense creator may edit or soft-delete a friendship-context expense.** Today any friendship member can; the client UI already gates the Edit/Delete affordances on `expense.createdBy == currentUser.uid`, but a custom client or a future bug could issue the write directly and the rules would accept it. PR #46 made the gap reachable from a production UI codepath (the Expense Detail edit/delete actions) for the first time, raising the urgency to close it server-side.

Current state (read it; do not re-derive):

- `firestore.rules:282-308` — `isValidExpenseUpdate()` preserves `createdBy`/`createdAt` immutability (`data.createdBy == prev.createdBy`) but does **NOT** require `request.auth.uid == prev.createdBy`, so `allow update: if isCallerFriendshipMember() && isValidExpenseUpdate()` accepts an edit or soft-delete from **either** member. Hard delete is already `allow delete: if false` (clients soft-delete via update setting `deleted: true`). `isValidExpenseCreate()` already gates create on `data.createdBy == request.auth.uid`.
- `functions/test/firestore-rules/expenses-friendship.test.ts:606-647` — the `FR-EX-06 additions` describe block. Two tests currently assert `assertSucceeds(...)` for a NON-creator member's update and soft-delete, each with a self-documenting comment: *"Flip to assertFails when the rules-hardening PR adds `request.auth.uid == prev.createdBy` to `isValidExpenseUpdate()`."* These document today's permissive behaviour and are the exact tests this PR inverts.
- `docs/sprint-zero/stories/FR-EX-06-edit-delete-expense.md` §2.9 item 5 + preconditions §3 — the creator-only intent (the UI gate + the planned rules-side defence-in-depth re-check).
- The PR #46 reviewer note R-2 (linked from issue #47) — the origin of the gap.

RECOMMENDED scope (ship this):

- **Add the creator-only gate to `isValidExpenseUpdate()`** exactly as the test comments specify: `&& request.auth.uid == prev.createdBy` (where `prev = resource.data`, the pre-update document). This restricts BOTH the edit path and the soft-delete path (both flow through `update`) to the original creator. Keep every existing clause (`isValidExpenseShared`, the `createdBy`/`createdAt` immutability locks, `updatedAt == request.time`) unchanged. Optionally extract an `isCallerExpenseCreator()` helper (`request.auth.uid == resource.data.createdBy`) for readability; either form is acceptable — the architect's call.
- **Invert the two existing "currently allow" tests** at `expenses-friendship.test.ts:612-647` from `assertSucceeds` -> `assertFails` (a non-creator member can no longer edit or soft-delete) and update their names/comments to assert the NEW behaviour.
- **Add the positive counterparts:** new `assertSucceeds(...)` cases proving the CREATOR (memberA) can still edit and still soft-delete via the same shapes, so the tightening does not regress the legitimate path.
- **Confirm the non-member negative still holds** (an outsider / non-member is still rejected — likely already covered earlier in the suite; add one explicit case if absent).
- **No client / UI change, no Cloud Function, no trigger change, no schema change, no index change.** The client already gates Edit/Delete on `createdBy`; the `onExpenseWriteFriendship` trigger recomputes on any write regardless of author; `simplifiedBalances` rules are untouched (Invariant 2 reinforced, not modified).

ESCALATION (architect decides at kickoff):

- **Creator-only, or either-member, soft-delete?** This is the one genuine product question. A shared expense affects BOTH members' balances, so there is a coherent argument that either member should be able to delete it. BUT the FR-EX-06 client UI, the FR-EX-06 §2.9 item 5 note, and issue #47 all specify **creator-only**, and that is the defence-in-depth posture this PR exists to enforce. RECOMMEND **creator-only for both edit and soft-delete** (the minimal, client-matching fix). If the architect instead rules that either member may soft-delete, that is a deliberate product divergence requiring a paired client-UI follow-up (the Delete affordance would need to un-gate) — out of scope here; do NOT split the difference silently.
- **Note the settlement asymmetry — do NOT "harmonise" it.** `firestore.rules:488-489` deliberately lets **either party** soft-delete a settlement ("either party may soft-delete; nothing else changes"). Settlements are bilateral; friendship-expenses are creator-owned. This PR must NOT touch the settlement path or try to make the two symmetric — the asymmetry is intentional. Call it out in the Architect Notes so a future reader does not "fix" it.
- **`fix` vs `chore` type.** The change rejects previously-accepted writes (a security-gap closure), so `fix(rules):` is defensible; `chore(rules):` is also acceptable for a hardening with no user-facing behaviour change. Architect's call; single-token scope either way.
- **New ADR?** Likely NOT — this is a tightening WITHIN the existing rules authorization model (ADR-0008 client user-doc writes / ADR-0010 field-level rules / Invariant 2), not a new decision. RECOMMEND a short Architect Notes block on the story rather than a full ADR; the architect may file one if they judge the creator-only-vs-either-member ruling ADR-worthy.

Story points: **2** (rules one-liner + test inversions + two new positive tests + the rules-suite run + planning-doc reconciliation).
