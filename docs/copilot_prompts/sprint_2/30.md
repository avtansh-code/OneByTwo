## 1. Scope — what we build

**Cross-launch persistence for the two documented in-memory deferrals.** Both shipped as best-effort-but-session-only because `shared_preferences` was not in the lockfile; this chore adds it (behind a thin seam) and makes both survive an app restart:

1. **Notifications `wasPermanentlyDenied` (FR-AC-04 / PR #53 §2.6).** `lib/features/notifications/application/notification_permission_controller.dart` holds an in-memory `bool _wasPermanentlyDenied` (line 92, getter line 97), set on the deny/error transitions (lines 133, 138). The `notifications_lifecycle_host.dart:218` consumer reads `controller.wasPermanentlyDenied` to suppress the pre-permission dialog auto-trigger. Today the controller's own dartdoc (lines 82-90) and the README state the FR-AC-04 "do not re-show on **next launch**" semantic is approximated as "do not re-show **this session**" — a documented deviation tracked by the `// TODO(flutter-dev): persist wasPermanentlyDenied across launches once shared_preferences is added` at line 89-90. **This chore closes that TODO**: the flag is loaded at startup and persisted on the deny transition, restoring the true cross-launch semantic.
2. **FR-SE-09 reminder cooldown (FR-SE-09 §2.6 / PR #53 §2.6).** `lib/features/reminders/application/reminder_cooldown_provider.dart` is a `StateProvider.family<DateTime?, String>` keyed by `friendshipId`, holding the server-returned `nextAllowedAt` so the OBTSettleUpCard receiving-direction variant renders the disabled-with-countdown state. It is in-memory only and RESETS on launch (its dartdoc lines 18-19 explicitly name the deferred `shared_preferences` pairing). **This chore persists it** so a 24-hour cooldown is still honoured after a restart — the server (`notifications.md §6.1`) remains the authoritative gate; the persisted client value stays a best-effort UX optimisation.

## 5. Cross-cutting dependencies and risks

- **iOS Podfile.lock is the highest-risk surface.** A new native plugin bumps `ios/Podfile.lock`; forgetting to `pod install --repo-update` + commit it fails the CI "Build iOS (no signing)" job (which runs vanilla `pod install`). Mirror the #70 / `cloud_functions` precedents. Confirm the diff adds only the `shared_preferences_foundation` pod with no collateral Firebase version bumps. Keep free macOS runners only (`macos-15`).
- **Async/sync boundary.** `SharedPreferences.getInstance()` is async but the `NotificationPermissionController` is a sync `Notifier`. Resolve by loading the instance ONCE in `main()` and injecting a sync-getter wrapper — do NOT make `build()` async or block the first frame. A deep-link / auth transition arriving before hydration must not crash (the store is loaded before `runApp`, so it is always ready by the time any provider reads it).
- **Plugin platform-channel in tests.** `shared_preferences` calls a platform channel unavailable in `flutter test`. Bind all consumers to the `KeyValueStore` seam and override it with a fake in unit/widget tests (the `UrlLauncherService`/`AppSettingsService` pattern) — never call the plugin (or `SharedPreferences.setMockInitialValues`) from a feature test.
- **Do not regress existing behaviour or tests.** The session-scoped suppression states (`dismissedThisSession`, `notDetermined`) stay; only the cross-launch flag is added. The cooldown's server-authoritative gate and its disabled-with-countdown UI are unchanged — persistence only restores the countdown after a restart. The existing `reminder_cooldown_provider_test.dart` and the permission-controller tests must keep passing (extend, don't rewrite).
- **Expiry correctness.** A persisted cooldown whose `nextAllowedAt` is already in the past must hydrate as `null` so a long-closed app never shows a phantom countdown.
- **Do NOT widen scope.** This is ONLY the two named deferrals. Do not opportunistically persist other ephemeral state (theme, last-tab, draft expenses, onboarding flags) — each is its own future chore.
