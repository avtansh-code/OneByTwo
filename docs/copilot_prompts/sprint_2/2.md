PHASE 1 — RESOLVE THE CROSS-USER QUERY ARCHITECTURE (CRITICAL)
────────────────────────────────────────

Owner: architect. This phase produces ADR-0014.

This decision must be resolved BEFORE any matching code lands, because it determines whether a Cloud Function is needed, what shape the matching repository takes, and what the Firestore Security Rules look like.

The architect produces ADR-0014 at `.github/shared/decision-log.md`. Title: "Cross-user lookup for contact matching: open query, restricted query, or Cloud Function gateway."

The ADR must present three options honestly:

  **Option A — Open phone-number query against users collection:**
  - Firestore rule: `allow read: if request.auth != null && resource.data.phoneNumber == request.query.<phoneNumber filter>`. Effectively, any authenticated user can query `users` filtered by exact phone number and get back at minimum the matching document.
  - Privacy: any authenticated user can confirm whether a phone number is on OneByTwo. Enumerable by anyone with a phone-number list.
  - Usability: simple, single round-trip, no Cloud Function dependency.
  - Splitwise and most expense-share apps use this pattern.
  - Cons: trivially scriptable to map "is +91XXXXXXXXXX on OneByTwo" for arbitrary phone numbers, including ones the attacker doesn't know personally.

  **Option B — Restricted query (only existing friendships/group members):**
  - Firestore rule: `allow read: if request.auth != null && resource.id in <user's friendships' memberIds union groups' memberIds>`.
  - Privacy: high. You can only fetch users you already share a relationship with.
  - Usability: BROKEN for matching. You can't find someone to friend if the rule requires you to already be friends.
  - Effectively unusable for the matching purpose.

  **Option C — Cloud Function gateway (recommended):**
  - A new callable Cloud Function `lookupUserByPhoneNumber` takes an E.164 phone number and returns either `{ matched: false }` or `{ matched: true, displayName: string, photoUrl: string | null }`. NEVER returns the userId, phoneNumber back, or any other field.
  - The function performs the Firestore query server-side (where it has elevated permissions) and shapes the response to leak the minimum information needed.
  - Rate-limited per-user (e.g., 100 lookups per hour) to prevent enumeration attacks.
  - Logs each lookup (without the phone number itself, only a hash) for abuse detection.
  - Firestore rule: clients cannot read the `users` collection by phone-number query at all; only the function's service account can.
  - Privacy: medium. Confirms OneByTwo membership but doesn't expose userId or other fields. Rate-limiting prevents bulk enumeration.
  - Usability: an extra round-trip through the function (~200-400ms cold-start, ~50-100ms warm).
  - Cons: more moving parts; another Cloud Function to maintain; cold-start latency on the matching path.

The architect picks one and records the decision in the ADR. **Recommended choice: Option C**, because Option A makes the user base trivially enumerable (a real concern for a phone-only-auth app), Option B is functionally broken, and Option C's rate-limiting + minimised-response shape balances privacy with usability acceptably.

The ADR must close with: "Implication for PR #32:" specifying:
- Whether a Cloud Function is added in this PR.
- The exact shape of the function's input/output (or, if Option A, the exact Firestore query and rule shape).
- The shape of the matching repository on the client.
- The rate-limit policy (if Option C).

For the rest of this prompt, the assumption is **Option C — Cloud Function gateway is selected**. If the architect picks Option A or B, the entire Phase 4 and Phase 5 sections must be revised; the orchestrator pauses and re-confirms before proceeding.

PHASE 3 — ARCHITECT NOTES
────────────────────────────────────────

Owner: architect.

Append `## Architect Notes` to the matching story file covering:

3.1  Cloud Function shape (per ADR-0014 Option C):
     - Name: `lookupUserByPhoneNumber`.
     - Region: `asia-south1` (the established convention).
     - Input contract: `{ phoneNumber: string }` where phoneNumber is E.164 (`+91XXXXXXXXXX`). Validated via the same regex used client-side. Reject INVALID_INPUT for malformed.
     - Output contract: `{ matched: false }` OR `{ matched: true, displayName: string, photoUrl: string | null, otherUserId: string }`. The `otherUserId` is needed for friendship-document creation; this is the one piece of identifying information that crosses, and is acceptable because the calling user is about to create a friendship with that user (which will store the userId anyway).
     - Rate-limit policy: 100 lookups per user per hour. Store the rate-limit counter in Firestore at `_rateLimits/{userId}/lookups`. Returns RATE_LIMITED if exceeded.
     - Error envelope: typed per `cloud-functions-error-codes.md`. New error codes added: USER_NOT_FOUND (the phone number is not on OneByTwo — note: NOT used; this is the `matched: false` path, not an error), INVALID_INPUT (malformed phone number), RATE_LIMITED, INTERNAL.
     - Audit log: each invocation logs a hashed phoneNumber + timestamp + caller userId + matched/unmatched. Retention: 30 days for abuse detection; document this in `pii-handling.md`.

3.2  Matching repository shape on the client:
     - `MatchingRepository.lookupUser(phoneNumber: string) → Future<MatchResult>` where MatchResult is a sealed union: `Matched(displayName, photoUrl, otherUserId)`, `Unmatched`, `Failed(error)`, `RateLimited`.
     - Calls the Cloud Function via the Firebase Functions SDK.
     - Maps function-side error codes to domain-level errors per the auth-flow precedent.
     - The repository is the boundary that needs a contract test (per PR #30's pattern): assert that the phoneNumber argument is E.164 before the function call.

3.3  Friendship creation:
     - Client-side direct Firestore write (per ADR-0007 — user-authored data lives client-side, not server-side, unless invariant #2 says otherwise). No Cloud Function for the creation itself.
     - The `friendships/{friendshipId}` document ID is deterministic to enforce idempotency: hash both userIds (sorted) and use the result as the document ID. This way attempting to create a duplicate friendship is a no-op (or detectable via a `set` with `merge: false` failing if the doc exists).
     - Friendship document fields per the schema: `memberIds` (sorted array of two userIds), `createdAt`, `createdBy`, `simplifiedBalances` (initial empty/zero map, server-managed thereafter).
     - The `createdBy` field is provenance, not authority — both members are equal once the friendship exists.

3.4  Firestore Security Rules updates:
     - **Users collection rule update:** under Option C, clients cannot query `users` by phoneNumber. Tighten the existing read rule to only allow reads of (a) the user's own document, OR (b) other documents only when the calling user is in a friendship/group with that user. The matching function bypasses this via service-account.
     - **Friendships collection rules:**
       * `allow create: if request.auth.uid in request.resource.data.memberIds && request.resource.data.memberIds has length 2 && request.resource.data.simplifiedBalances == empty/zero`.
       * `allow read: if request.auth.uid in resource.data.memberIds`.
       * `allow update: if request.auth.uid in resource.data.memberIds && only the user-authored fields are changing` (similar field-level diff pattern as users update from PR #12). The `simplifiedBalances` field is server-only-writable.
       * `allow delete: if request.auth.uid in resource.data.memberIds && resource.data.simplifiedBalances has zero net for this pair` (deferred — friendship deletion is FR-FR-05, not in this PR. For PR #32, default-deny delete is acceptable).
     - Each rule has at least three negative tests (parallel to PR #12's user-update rule pattern).

3.5  Self-add and duplicate-friendship guards:
     - Client-side: before initiating the lookup, check if the phoneNumber matches the current user's phoneNumber; if so, block immediately with the spec-specified message. This avoids wasting a function call on a guaranteed self-match.
     - After matching: check if a friendship between the two userIds already exists (compute the deterministic document ID and check existence). If it exists, navigate to it instead of attempting creation.

3.6  Coverage gate posture:
     - `lib/features/friends/**` already cleared the gate in PR #31. PR #32 adds matching/repository/friendship-creation code; the gate continues to apply.
     - `functions/src/lookup-user-by-phone-number/**` is a NEW module folder. Per the gate, it must be ≥70% covered from this PR's first merge. Functions-dev plans the test suite accordingly.
