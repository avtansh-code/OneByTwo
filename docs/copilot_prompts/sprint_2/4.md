PHASE 2 — ARCHITECT NOTES
────────────────────────────────────────

Owner: architect.

Append `## Architect Notes` to the story:

2.1  **Net-balance computation and INR formatting — both belong in `lib/core/`.**
     - The net-balance function is a pure transformation: `int Function(Map<String, Map<String, int>> simplifiedBalances, String currentUserId, String otherUserId)`. It returns the SIGNED paise amount from the current user's perspective (positive = "owes you", negative = "you owe", zero = "settled up"). File: `lib/core/balances/net_balance.dart`. This is the read-side companion to the simplified-debts algorithm in `functions/src/simplified-debts/` (PR #12) and shares the same domain model.
     - The INR formatter takes `int paise` and returns the localised display string per SRS section 5.9 (Indian numbering system, e.g., `₹1,23,456.00`). File: `lib/core/formatters/inr_formatter.dart`. **Single source of truth.** Every Widget that displays a balance imports this formatter; no inline paise→rupee maths anywhere else in the codebase. The PR #34 precedent for `lib/core/widgets/india_phone_input_formatter.dart` justifies this layout — formatters are core, not feature-scoped.
     - Both functions have their own unit-test files (see Phase 4).

2.2  **Repository layer — extend `FriendshipRepository` with a list query, do not fork.**
     - Add `Stream<List<FriendshipDoc>> watchFriendships(String currentUserId)` that returns a real-time Firestore snapshot stream filtered by `where('memberIds', 'array-contains', currentUserId).orderBy('lastActivityAt', descending: true)`. This requires a composite index — declare it in `firestore.indexes.json` and document the new index in the spec.
     - Add a `FriendshipDoc` value type (immutable, with `memberIds`, `simplifiedBalances`, `lastActivityAt`) — pure data, no formatting logic. Place in `lib/features/friends/domain/`.
     - Do NOT modify `createFriendship` or `friendshipExists`. PR #32's boundary contract for the write path is locked in.

2.3  **Presentation layer — replace, do not extend, the placeholder screen.**
     - The current `friends_list_screen.dart` (PR #14 placeholder) becomes the real screen. Preserve the `_onAddFriendTapped` handler that pushes `AddFriendScreen` and the existing `friend_add_button_tapped` telemetry.
     - Use a `StreamProvider<List<FriendListItem>>` (Riverpod) to wrap the repository stream and project documents into `FriendListItem` records (`friendshipId`, `displayName`, `photoUrl`, `netBalancePaise`). Display-mapping (paise → INR string, balance direction) is computed in the widget using the shared formatter; the provider returns the structured paise integer, not the formatted string.

2.4  **Friend display-name resolution — open architectural question.**
     - The `friendships` doc contains `memberIds` (UIDs only). The friend's `displayName` and `photoUrl` live on the `users/{otherUserId}` doc. Two reasonable options:
       (a) Issue N parallel `users/{uid}` lookups from the stream's `map`. Simple, but O(N) reads per snapshot delivery.
       (b) Add a Riverpod `userProfileProvider.family(uid)` that caches per-user reads and listens for changes. More moving parts but no redundant reads.
     - Pick option (b) if the architect agrees the caching value justifies the indirection. Otherwise (a) is acceptable for v1.0 — friend counts are bounded by ADR-0013's contact-matching premise.
     - Whichever is chosen, NEVER fan out a user-doc read for a friend whose `displayName` is already cached. Cache invalidation rides on the user-doc snapshot listener if option (b).

2.5  **Real-time updates (AC-6) — favour Firestore snapshot listener, not polling.**
     - The Riverpod `StreamProvider` directly subscribes to the Firestore snapshot stream. Updates to `simplifiedBalances` or `lastActivityAt` flow through automatically. Verify the list re-orders when a row's `lastActivityAt` changes — the provider's projection must respect the order coming from Firestore.

2.6  **Friend-detail navigation stub (per Phase 0.2).**
     - `OnTap` on a row fires `friend_row_tapped` with a hashed `friendship_id`, then either:
       (a) pushes a placeholder `FriendDetailScreen` that displays only the friendship ID and a back button, OR
       (b) opens a SnackBar saying "Friend detail coming soon" and does not navigate.
     - The architect chooses one. Document the choice and the natural removal moment (FR-FR-04 PR).

2.7  **Composite index** — adding the `memberIds, lastActivityAt` composite index to `firestore.indexes.json` is a deployment artefact. Note in architect notes that the index must be deployed before the PR is merged to production (handled by devops in Phase 5).

2.8  **No new ADR required.** All architectural moves above are within precedent. If the friend display-name resolution discussion reaches a point where it would change schema or trigger a Cloud Function call, that escalates to a new ADR — escalate to architect before adding such a call.
