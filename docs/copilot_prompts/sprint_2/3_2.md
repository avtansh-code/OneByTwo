PHASE 1 — STORY READINESS (PM)
────────────────────────────────────────

PM agent confirms FR-FR-02 story file is DoR-compliant. The ACs should be:

  - Given the user is on the Friends-add entry point, when they choose "type number" (or equivalent per the screen spec), then a phone-number entry screen appears with a locked +91 prefix and a 10-digit input field.
  - Given the user enters a valid 10-digit number and taps Continue, when matching completes, then the same flow as FR-FR-01 proceeds (match found → friendship created or existing; no match → share sheet).
  - Given the user enters a number with the same E.164 representation as their own phone, when they tap Continue, then the self-add guard from `MatchAndInviteController` triggers and the user sees the same error UI as in FR-FR-01.
  - Negative: given the user enters an invalid number (less than 10 digits, non-numeric, etc.), when they tap Continue, then validation prevents the call and shows inline error per the spec.
  - Negative: given the user enters a number that's well-formed but the Cloud Function lookup fails, then the same error UI from FR-FR-01 appears.

DoR §9 invariant applicability:
  - Invariant #1 (paise): N/A.
  - Invariant #2 (simplifiedBalances): APPLIES indirectly via the friendship creation path — same protections as FR-FR-01.
  - Invariant #3 (system share sheet): APPLIES via the no-match path — same path as FR-FR-01.
  - Invariant #4 (single Firebase project): APPLIES.
  - Invariant #5 (PII handling, if promoted): APPLIES — the typed phone number is in-memory only, never logged or analytics-parameterised.

Telemetry events:
  - `friend_manual_entry_opened`.
  - `friend_manual_entry_submitted` (no PII; just an event).
  - `friend_manual_entry_validation_failed` (with error code: too short / non-numeric / etc.; no PII).
  - The downstream events from PR #32 (`friend_matching_started`, `friend_match_found`, etc.) fire from the shared controller and do not need to be re-emitted from this PR's code.
