## 1. Scope — what we build

FR-AU-09 (SRS section 4.1, line 168, **P1**): "The user shall be able to permanently delete their account, which triggers a Cloud Function that anonymises their data in shared groups and removes personal records within 30 days." Entry point is the Profile screen "Delete Account" row (SCR-26), which today fires a `'Coming soon'` snackbar dead-end (`lib/features/profile/presentation/profile_screen.dart` lines 387-401). The flow is **SCR-28 Part B: Account Deletion** — a multi-step full-screen route `/profile/delete-account` (Step A warning -> Step B re-authentication -> Step C type-`DELETE` confirmation -> Step D processing -> Step E success -> Phone Entry, stack cleared).

RECOMMENDED scope (ship this):

- **New callable Cloud Function `deleteUserAccount` (region-pinned `asia-south1`).** SCR-28 Step D names it `deleteUserAccount`. Follow the existing callable boundary pattern (`functions/src/send-reminder-notification/function.ts` — auth check first (`UNAUTHENTICATED`), then the work; `HttpsError` from `firebase-functions/v2/https` with the catalogue code carried in `details.errorCode` per `docs/design/07-technical/cloud-functions-error-codes.md`). Export from `functions/src/index.ts` with the `REGION` const. The function authenticates the caller (`request.auth.uid`), then performs the cascade fan-out **using the Admin SDK** (it bypasses security rules by design — clients have NO delete path; see §5). Account deletion is an explicitly server-side responsibility (SRS lines 93, 405, 473).

- **Cascade fan-out: DELETE personal records, ANONYMISE shared data.** This is the core architectural decision (architect-owned, ADR-0016). The SRS (line 168) requires "anonymises their data in shared groups and removes personal records." Concretely:
  - **DELETE (personal):** `users/{uid}` doc; `activity/{uid}/items/**` (the user's own feed); `_rateLimits/{uid}/**`; the Storage avatar `avatars/{uid}`; and finally the Firebase **Auth** record via `admin.auth().deleteUser(uid)`.
  - **ANONYMISE / PRESERVE (shared):** `friendships/{*}` where the user is a member, and their `expenses` subcollections + related `settlements` — the OTHER member must retain their balance and history. Do NOT delete the friendship doc and do NOT zero or recompute the other member's `simplifiedBalances` (Invariant 2 — see §4). The deleted user simply becomes a non-resolvable UID; the client already renders an absent user-doc as a name fallback (`lib/features/friends/application/friends_list_provider.dart:109` — `displayName ?? 'Unknown'`).

- **"Unknown" vs "Deleted User" reconciliation (resolve in this PR).** SCR-28 Part B specifies the deleted user shows as **"Deleted User"**, but the shipped client fallback for an absent user-doc renders **"Unknown"** (`friends_list_provider.dart:109`, `friend_detail_provider.dart:289`, `activity_feed_screen.dart:297`). The architect/PM decides: (a) change the client fallback string to "Deleted User" (simplest, but conflates a transient missing-doc read with a real deletion), or (b) have `deleteUserAccount` write a lightweight tombstone (e.g. a `deletedUsers/{uid}` marker, or a PII-free `users/{uid}` shell with `displayName: 'Deleted User'`) that the client resolves to "Deleted User" while keeping "Unknown" for genuine read gaps. RECOMMEND (b) if cheap; otherwise (a). State the decision in the ADR and the story.

- **Re-authentication reuses FR-PR-02, do not fork it.** SCR-28 Step B is exactly the re-auth pattern FR-PR-02 just shipped: pre-filled read-only current number -> Send OTP -> OTP entry -> on success advance. Drive it from `PhoneAccountRepository.reauthenticate` (`lib/features/auth/data/phone_account_repository.dart:45`) / `currentPhoneNumber()` (`:21`). Do NOT re-implement OTP entry or the +91 flow; reuse the auth OTP widgets as FR-PR-02 does. `requires-recent-login` is load-bearing here too (FR-AU-07 session persistence) — the re-auth IS the recent-login refresh that lets the subsequent `deleteUserAccount` proceed.

- **Type-`DELETE` confirmation gate (Step C).** Exact match `DELETE` (case-sensitive, trimmed); the "Delete My Account" button stays disabled until it matches. No Firestore/Function call before the gate passes.

- **Processing + timeout + success (Steps D/E).** Step D blocks back navigation; a 30-second `deleteUserAccount` timeout returns to Profile View with an error snackbar carrying a "Contact Support" action (reuse the FR-PR-05 `ContactSupportController`). Step E shows the success state for 3 s, then clears the stack to the Phone Entry screen. Note the eventual-consistency edge cases (SCR-28 Account Deletion edge cases 3/4): the function may complete server-side even if the client times out or is force-quit — so the function MUST be idempotent (§5).

- **Telemetry (PII-free) — already pre-declared.** The seven events already exist in `docs/design/07-technical/telemetry-plan.md §1.7` (lines 225-231): `delete_account_started`, `delete_account_warning_continued`, `delete_account_warning_cancelled`, `delete_account_reauth_completed`, `delete_account_confirmed`, `delete_account_completed`, `delete_account_failed` (`error_code`). Wire them; do NOT re-declare. The `uid` / phone number must NEVER be a parameter (SRS line 308); server-side structured logs hash the uid via `functions/src/utils/id-hash.ts` (`hashId`), consistent with the reminder callable.

- **No money rendering.** FR-AU-09 has no monetary surface of its own — Invariant 1 is N/A. Do NOT add or recompute balances (see Invariant 2 in §4).

ESCALATION (architect decides at kickoff):

- **The "within 30 days" mechanism.** Synchronous hard-delete inside the callable (immediate fan-out; "30 days" is then user-facing copy / a safety ceiling) vs. a soft-delete tombstone + a scheduled cleanup (`onSchedule`) reaper that hard-deletes after a grace window. RECOMMEND the synchronous hard-delete for v1.0 (simplest, no new scheduler, matches the callable contract SCR-28 Step D expects) and file the scheduled-cleanup / grace-period as a FUTURE issue (SCR-28 Account Deletion Open Questions 1-3). The architect ratifies.
- **Atomicity / batching.** A user with many expenses/settlements may exceed the 500-write `WriteBatch` cap. RECOMMEND chunked batched writes (or a `BulkWriter`) with idempotent re-run semantics; the architect ratifies the exact shape and the step order (delete Firestore data -> delete Storage -> delete Auth LAST, so a mid-failure leaves a re-runnable state with the Auth record still present).
- **Designer involvement.** Whether the delete screens get net-new component specs or are documented as a reuse of the existing OTP + re-auth screens with deletion-scoped copy (SCR-28 already specifies the layout, so likely a reuse note).

Story points: **8** (per the carry-forward "~5-8 SP", taken at the high end given the new Cloud Function + cascade fan-out + 3-step UI + re-auth reuse + the unit/integration/rules test surface): 2 — the `deleteUserAccount` callable + cascade fan-out + idempotency + Admin-SDK Auth delete; 1 — the anonymise-vs-delete matrix + the "Deleted User" tombstone/fallback decision + Inv-2-safe handling; 1 — the multi-step delete flow controller (Steps A-E) reusing FR-PR-02 re-auth; 1 — the Profile entry-point wiring + processing/timeout/success states + Contact Support reuse + telemetry; 1 — the Functions unit + emulator integration tests (cascade correctness, idempotency, other-member balance preserved); 1 — Flutter widget/controller tests incl. every negative case + boundary contract; 1 — rules confirmation that client delete stays denied + docs/ADR.

## 5. Cross-cutting dependencies and risks

- **Idempotency is load-bearing, not optional.** SCR-28 edge cases 3 and 4: the client may time out or be force-quit while `deleteUserAccount` runs server-side, and the user may retry. A second invocation after a partial or complete delete must not throw an unhandled error — re-running on an already-deleted user should resolve cleanly (treat "auth user already gone" / "doc already absent" as success). Order the steps so Auth deletion is LAST: while the Auth record exists the caller can still re-authenticate and retry; once Auth is gone the account is unreachable.
- **Client has NO delete path — keep it that way.** `firestore.rules` denies `delete` on `users` (`allow delete: if false`) and on friendships/settlements; the Admin SDK in the function bypasses rules. Do NOT add any client-side `allow delete` to satisfy this feature. Functions Dev should add/confirm a rules test that a client delete of `users/{uid}` (and a friendship) is still rejected.
- **Other-member balance preservation.** The single highest-risk regression: a naive "delete everything the user touched" would destroy the surviving member's history/balance. The integration test MUST assert that after deleting user A, user B's `friendships/{A_B}.simplifiedBalances` and settlement/expense history are intact, with A rendered as the deleted-user fallback.
- **Re-auth reuse coupling.** Reuse `PhoneAccountRepository` from FR-PR-02 (#64). If its surface needs a tiny extension (e.g. a reauth-only path that does not also update a number), prefer extending that repository over forking — keep the "never `signInWithCredential`" guarantee.
- **Groups are Sprint 3 (data-layer only).** `groups/{groupId}` exists in the schema but has no client UI and (per `firestore-schema.md`) no rules. The SRS says "anonymise in shared groups", but there are no live groups in v1.0 — implement the friendship axis fully and stub / forward-compat the group axis (a TODO + an ADR note), exactly as prior PRs stubbed the group axis. Do NOT build the Groups epic here.
- **Storage cleanup.** Delete `avatars/{uid}`; receipts under `receipts/friendships/{fid}/{expenseId}` are shared-context artefacts on surviving friendships — do NOT delete the other member's receipts. The architect specifies exactly which Storage paths are personal vs shared.
- **No new Flutter plugin expected.** `firebase_auth`, `cloud_functions`, `cloud_firestore`, `firebase_storage` are all already dependencies — so **no `ios/Podfile.lock` change is expected.** If the architect chooses a scheduled reaper, that is a Functions-only `onSchedule` addition with its own region pin + tests, no client plugin.
