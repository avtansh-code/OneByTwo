7. ## 1. Scope — what we build

8. FR-AC-05 (SRS section 4.7, line 240, **P0**): "Tapping a notification shall deep-link the user to the relevant screen, even from a cold start." The resolver + navigation + the four dispatch sources shipped in #53; what was **deferred from #63** (which built the controller seam) is the **tab-switch**: today a notification tap pushes the detail screen onto the **root** navigator over **whatever primary tab happened to be active**, and never drives the bottom-nav selection — so the user lands in (and on pop returns to) a stale, unrelated tab. This PR makes a notification deep-link **select the correct primary tab** via `shellNavigationControllerProvider.selectTab(...)` before/with the push, so FR-AC-05 lands the user in the **relevant tab context** with a coherent back-stack.

9. Current state (read it; do not re-derive):
   - `lib/core/routing/notification_deep_links.dart` — the pure resolver `NotificationDeepLinks.resolve(payload, currentUid)` -> a sealed `DeepLinkTarget` (`DeepLinkExpenseDetail`, `DeepLinkFriendDetail`, `DeepLinkUnavailable`, `DeepLinkGroupsComingSoon`), plus `navigate(context, target)` which **only** `Navigator.of(context).push`-es `ExpenseDetailScreen` / `FriendDetailScreen` (or shows a snackbar). It has **no `ref`/container**, so it cannot touch the shell controller today.
   - `lib/features/notifications/application/deep_link_handler.dart` — `DeepLinkHandler` (holds a `ProviderContainer _ref`) resolves, emits the PII-free `fcm_notification_tapped` event (`notification_type` + `source` only), then calls `navigate`.
   - `lib/features/notifications/presentation/notifications_lifecycle_host.dart` — wires the **four** dispatch sources (`DeepLinkSource.foreground` in-app banner tap, `background` `onMessageOpenedApp`, `coldStart` `getInitialMessage`, and the cold-start-after-sign-in **replay** of `pendingDeepLinkProvider`). It sits below `MaterialApp` (via `MaterialApp.builder`) and dispatches with its own `context` -> the **root** navigator.
   - `lib/features/shell/application/shell_navigation_controller.dart` — the #63 `shellNavigationControllerProvider` (`NotifierProvider.autoDispose<ShellNavigationController, int>`, `selectTab(int)` ignores out-of-range; emits NO telemetry). `AuthenticatedShell` `ref.watch`es it as the `IndexedStack` index (`authenticated_shell.dart:133`) and already calls `selectTab` from user taps (`:95`), the Android-back snap-to-0 (`:141`), and the FR-PR-04 Profile rows (`selectTab(1)`/`selectTab(2)`).
   - The **Activity feed row-tap** (`activity_feed_screen.dart`) ALSO consumes `NotificationDeepLinks.resolveFromFields` from **within the Activity tab** — it is an in-tab navigation and must NOT switch tabs.

10. RECOMMENDED scope (ship this):

    - **Drive the shell tab from the deep-link dispatch (the core change, architect-owned, ADR-0018).** Thread the `shellNavigationControllerProvider.notifier.selectTab(...)` call into the **FCM deep-link dispatch path** (the `DeepLinkHandler`, which already holds the container) so each tappable target selects its home tab BEFORE the root-navigator push, leaving a coherent back-stack. The Activity-feed in-tab row-tap path is explicitly excluded (no tab switch).
    - **Target -> primary-tab mapping (PM + designer + architect decision).** RECOMMEND: `DeepLinkExpenseDetail` and `DeepLinkFriendDetail` -> the **Friends tab (index 1)** (both are friends-cluster detail screens; the detail pushes over Friends so pop lands on Friends); `DeepLinkUnavailable` (e.g. `expense_deleted`) -> the **Activity tab (index 3)** + the existing "This item is no longer available" snackbar (the item lived in the activity feed); `DeepLinkGroupsComingSoon` -> no tab switch + the existing "Groups are coming soon" snackbar (forward-compat). The PM/designer ratify the mapping against SCR-25 (Activity) and the notification design.
    - **Cold-start + ordering correctness (the highest-risk surface).** The tab switch must occur only when `AuthenticatedShell` is mounted. For `coldStart`/the post-sign-in replay this is already guaranteed by the existing `_replayPendingDeepLink` post-`AuthenticatedWithProfile` `addPostFrameCallback`; for `background`/`foreground` the shell is mounted. Ensure `selectTab` runs before (or in the same frame as) the push so there is no visible flash of the wrong tab, and that a deep-link arriving while a non-shell route is on top (e.g. mid-onboarding) still behaves (it caches to `pendingDeepLinkProvider` today — preserve that).
    - **Telemetry (PII-free) — extend, do not re-declare carelessly.** Keep `fcm_notification_tapped` (`notification_type`, `source`). If the architect wants to observe the tab-switch, add at most a **non-identifying** `target_tab` enum param (e.g. `'friends'`/`'activity'`/`'none'`) to the existing event — NOT a new event, NOT any `uid`/`friendshipId`/composite. Confirm with the PM; the `uid`, any friendship composite, and raw entity IDs must NEVER be a parameter (SRS line 308 / ADR-0013).
    - **No new Cloud Function, no rules change, no schema/index change, no new plugin.** This is a pure client-side navigation refinement over existing providers. Invariants 1 and 2 are N/A (no money, no `simplifiedBalances`); no `ios/Podfile.lock` change.

11. ESCALATION (architect decides at kickoff):

    - **Where the tab-switch lives.** (a) In `DeepLinkHandler.handleDeepLink` (it already has the container — read `shellNavigationControllerProvider.notifier` and `selectTab` before calling `navigate`); vs (b) add an optional `tabIndex`/`int? Function()` selector or a `WidgetRef` to `NotificationDeepLinks.navigate`; vs (c) give each `DeepLinkTarget` a `homeTabIndex` getter and let the handler select it. RECOMMEND (a) + (c) (a small `homeTabIndex` on the sealed target keeps the mapping with the target and the side-effect in the handler), keeping `navigate` pure of Riverpod. Architect ratifies.
    - **Switch-then-push vs navigate-within-tab.** RECOMMEND keep the existing root-navigator push (the detail is presented full-screen above the shell) AND switch the underlying tab, so pop returns to the chosen tab — the minimal, lowest-risk change. A full per-tab Navigator migration is `go_router`/Sprint-3 territory and out of scope.
    - **Does the foreground in-app-banner tap switch tabs?** The user is already on a tab; RECOMMEND yes, for consistency (same handler), but confirm the UX with the designer (a banner tap that yanks the tab may surprise).
