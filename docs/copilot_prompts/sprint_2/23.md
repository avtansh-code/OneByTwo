RECOMMENDED scope (ship this):

- **Compose existing providers — no new data layer.** The friendship axis already exists:
  - `friendsListProvider` (`lib/features/friends/application/friends_list_provider.dart:48`, `StreamProvider<List<FriendListItem>>`) already yields per-friendship `FriendListItem`s carrying `displayName`, photo, and `netBalancePaise` (computed via `netBalancePaise()` in `lib/core/balances/net_balance.dart`).

The settle-up source parameter `'home_dashboard'` is ALREADY anticipated in `lib/features/settlements/application/settle_up_telemetry.dart:45` — reuse the existing flow, do not fork it.
- **Telemetry.** Emit the SCR-06 events: `home_viewed` (`net_balance_state`), `home_settle_up_tapped`, `home_tile_tapped`, `home_empty_cta_tapped`, `home_error_retry_tapped`, `home_error_support_tapped`. ## 4. Invariants

Read `.github/shared/invariants.md`. Relevance for this PR:

- **Invariant 1 (integer paise):** Balances are signed integer paise end to end; convert to INR only at the UI via `formatInrFromPaise()`. No `double`/`float` for money, no inline `/100`.
- **Invariant 2 (`simplifiedBalances` server-only):** The dashboard is READ-ONLY over `simplifiedBalances`. It must never write that field. The overall-net and top-5 projections are pure read-side reducers.
- **Invariant 3 (system share sheet only):** N/A to the dashboard itself. The error-state "Contact Support" link reuses the FR-PR-05 `mailto:` flow (not the share sheet) — do not route it through `ShareService`.
- **Invariant 4 (single Firebase project):** Reinforced — all reads come from the single production project via the emulator in CI.

## 5. Cross-cutting dependencies and risks

- **Design-system primitives DO NOT exist in `lib/core/widgets/` yet.** The SCR-06 spec's "Components Used" table references `OBTRupeeText` (Component 5), `OBTBalancePill` (Component 4), `OBTFriendListTile` (Component 16), `OBTEmptyState` (Component 18), `OBTErrorState` (Component 19), `OBTSkeletonLoader` (Component 20) per `docs/design/02-design-system/components.md`, but `lib/core/widgets/` contains only the confirmation dialog, phone formatter, amount input, activity row, bottom nav, and FAB. The friends feature has LOCAL widgets — `lib/features/friends/presentation/widgets/balance_pill.dart` and `friend_list_tile.dart`. **Architect's call at kickoff:** reuse the friends-local widgets from the home feature, or promote `balance_pill` / `friend_list_tile` (and extract `OBTRupeeText` / `OBTEmptyState` / `OBTErrorState`) to `lib/core/widgets/` now that a genuine second use site exists (the carry-forward list explicitly deferred several of these "until a second use site"). Prefer the minimum that avoids duplicating the balance-pill/tile logic; large primitive extractions can be their own follow-ups.
- **Settle-up reuse, not re-implementation.** Wire the existing settle-up bottom-sheet flow with `source: 'home_dashboard'`; do not duplicate settlement logic.
- **No charting dependency.** FR-HD-03 ships as a placeholder card only — do NOT add `fl_chart` or any plugin. No new Flutter plugin should be needed, so **no `ios/Podfile.lock` change is expected**. If the architect nonetheless adds any plugin, run `cd ios && pod install --repo-update` and commit `ios/Podfile.lock` in the same PR (the Build iOS CI job runs a vanilla `pod install` and fails on a stale lock — verified pattern, PR #55 lineage).
- **No new Cloud Function, Firestore collection, security rule, or index.** This is a 100% client-side, read-only PR composing existing providers.
