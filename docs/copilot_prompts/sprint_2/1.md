PHASE 1 — RESOLVE THE PRIVACY ARCHITECTURE DECISION (CRITICAL)
────────────────────────────────────────

Owner: architect. This phase produces ADR-0013.

This decision must be resolved BEFORE any UI code is written, because PR #31's controller contract — what data is exposed when a contact is selected — depends on it.

The architect produces ADR-0013 at `.github/shared/decision-log.md`. Title: "Contact matching strategy: local intersection vs server-side matching."

The ADR must present both options honestly:

  **Option A — Local matching (recommended):**
  - Contacts loaded into device memory only. Never uploaded anywhere.
  - To check whether a selected contact is a OneByTwo user, the app queries Firestore by `phoneNumber` (a single document read per selection). For "show me all my contacts who are already on OneByTwo" views, the app loads its own friends list (small) and intersects locally; broad-stroke "discover all OneByTwo users in my contacts" is NOT a v1.0 feature and is explicitly out of scope.
  - Pros: privacy-preserving by default, simpler, no Cloud Function dependency, no batch-upload of PII.
  - Cons: scaling beyond ~1000 contacts could become slow on cold devices (acceptable trade-off; v1.0 user base is well below this); requires Firestore queryable by `phoneNumber` (already true per PR #9 schema).

  **Option B — Server-side matching:**
  - Phone numbers (or hashed phone numbers) batched and sent to a Cloud Function that does the matching.
  - Faster at large scale, more efficient bandwidth-wise.
  - Pros: scales better, can implement privacy-preserving variants (hashing, k-anonymity, bloom filters).
  - Cons: PII transits to server even if hashed; adds Cloud Function complexity; harder to walk back the privacy posture later.

The architect picks one and records the decision in the ADR. Recommended choice: **Option A**, because v1.0's scale does not require server-side matching, and the privacy posture is hard to walk back. Server-side matching with privacy-preserving techniques can be revisited in a future sprint if scale demands.

The ADR must close with: "Implication for PR #31: …" specifying the controller's hand-off contract — what data is exposed when the user selects a contact, and what is NOT exposed. The hand-off contract is what the boundary-contract test (Phase 5 item 6) will assert.

For the rest of this prompt, the assumption is **Option A — local matching is selected**. If the architect picks Option B, the controller-contract sections of Phases 3 and 4 must be revised to reflect the different shape; the orchestrator pauses and re-confirms before proceeding.

PHASE 3 — ARCHITECT NOTES
────────────────────────────────────────

Owner: architect.

Append `## Architect Notes` to the story covering:

3.1  Contact-picker package choice:
     The Flutter ecosystem has multiple options (`flutter_contacts`, `contacts_service`, `fast_contacts`, etc.). Pick one and pin its version. Criteria:
     - Active maintenance.
     - Cross-platform parity (iOS + Android).
     - Lazy loading / virtualisation support for large contact lists.
     - Permission API that maps cleanly to the iOS/Android distinction (iOS only has "granted/denied/not-determined"; Android has additionally "permanently denied" via "don't ask again").
     - Document the choice with one sentence of rationale.

3.2  Permission flow:
     - First-launch path: tap "Add friend" → permission prompt → contact picker (or denied screen).
     - Subsequent-launch paths: prompt skipped if previously granted; "open Settings" path if previously denied.
     - Document a state machine: `not_determined → prompted → (granted | denied | denied_permanently)`.

3.3  Controller contract (the hand-off to PR #32):
     - Per ADR-0013, the controller exposes a `selectedContact` value and a `clearSelection()` method.
     - The `selectedContact` shape is specified explicitly: `{ displayName: string, phoneNumbers: List<string> }` (not the raw native contact object — this isolates PR #31 from PR #32's needs and keeps PII surface minimal).
     - **The phone numbers in the hand-off MUST be E.164 normalised** (`+91XXXXXXXXXX`) before being exposed to the boundary, because PR #32 will pass them to Firestore queries and PR #29 taught us that boundaries between controllers and repositories must agree on format. Normalisation happens INSIDE the controller before exposure.
     - The controller does NOT expose the full contact list to other parts of the app. The picker is a self-contained surface; only the selected contact crosses the boundary.

3.4  Privacy/PII guards (NEW PATTERN):
     - The contact list is held in a controller scoped to the picker route. When the picker is dismissed, the contact list is disposed and falls out of memory.
     - No contact data goes into:
       * Crashlytics breadcrumbs.
       * Analytics event parameters (event NAMES are fine; PARAMETERS containing names or numbers are not).
       * Logs (server or client).
       * Persistent caches (no `shared_preferences`, no Hive, no on-disk store of contacts).
     - Architect documents this in `docs/design/07-technical/pii-handling.md` (NEW DOCUMENT) — same author/structure as `cloud-functions-error-codes.md`, intended as the canonical PII-handling reference for every future PR that touches PII.

3.5  Testing strategy for the permission flow:
     - The permission state itself is OS-level and can't be perfectly faked in widget tests. Architect specifies the test seams: a permission-state provider that wraps the package's API, and an integration test that exercises the real OS permission via emulator capabilities (Android emulator can pre-grant permissions; iOS simulator is more limited).
     - Integration tests against Firebase services use the wrapper script from PR #30 (`scripts/dev/start-emulators.sh`) — never raw `firebase emulators:start`.

3.6  Coverage gate posture:
     - `lib/features/friends/**` is a new feature folder created by this PR. The CI coverage gate from PR #30 will apply to it from the moment the folder exists. Flutter-dev plans the test suite to clear ≥70% per-folder from this PR's first merge; lefthook scoped pre-push will enforce this locally.
     - Note explicitly: the gate is not a target to barely clear but a floor below which merge is impossible. Aim higher; design tests for behaviour, not coverage numbers.
