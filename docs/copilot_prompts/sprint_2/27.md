## 1. Scope — what we build

FR-HD-03 (SRS section 4.8, line 248, **P1**): "The Home dashboard shall show a current-month spend summary with a category breakdown (donut/bar chart)." It replaces the `SpendingBreakdownPlaceholderCard` ("Spending breakdown coming soon", 160 dp, `lib/features/home/presentation/widgets/spending_breakdown_placeholder_card.dart`) rendered under the "This Month" section header on the Home dashboard (`home_dashboard_screen.dart` line 388, SCR-06 Populated State, screen-spec `docs/design/06-screen-specs/06-08-home-and-search.md` lines 108-113). The placeholder card is superseded by a real card showing the current month's total spend plus a per-category breakdown chart.

RECOMMENDED scope (ship this):

- **The current-month per-category spend aggregation (the core read-path decision, architect-owned, ADR-0017).** This is the central architectural problem: **no cross-friendship expense read path exists today.** Expenses are read ONLY per single friendship (`ExpenseRepository.watchExpensesByFriendship({friendshipId, limit})` over `friendships/{fid}/expenses` with `where('deleted', isEqualTo: false).orderBy('date', descending: true)`; `lib/features/expenses/data/expense_repository.dart`). FR-HD-03 needs the **signed-in user's own spend** for the **current calendar month (IST, SRS section 5.9)**, grouped by `ExpenseCategory`. The architect ratifies the read path. RECOMMEND a **friendship fan-out**: reuse `friendsListProvider` (the FR-HD-01/02 source) to get the user's `friendshipId`s, then read each friendship's current-month, non-deleted expenses and aggregate **the user's own `sharePaise` from `splits`** per category — NOT the full `amountPaise` (the user's "spend" is their share, not the bill total). A `collectionGroup('expenses')` query is the alternative, but expenses carry no member field, so it cannot be scoped to the caller's friendships under the Security Rules (`firestore.rules` reads gate on friendship membership) without a schema change — RECOMMEND fan-out and forward-compat-stub the group axis (Sprint 3), exactly as `topBalancesProvider` stubbed groups.

- **Money is integer paise end-to-end (Invariant 1).** Aggregate every category total as an integer `*Paise` sum; convert to rupees ONLY at the UI via `formatInrFromPaise(int)` (`lib/core/formatters/inr_formatter.dart`). No `double`, no inline `/100`. The chart segment sizes are computed from integer paise ratios.

- **The category breakdown chart + a new charting plugin (architect + designer decision).** SCR-06 specifies "a donut or horizontal bar chart segmented by expense category using OBTCategoryChip colour mapping" (line 112). There is **no charting plugin** in `pubspec.yaml` today. Adding one (RECOMMEND `fl_chart`, the de-facto Flutter choice; the architect ratifies) is a **new Flutter plugin -> an `ios/Podfile.lock` change is REQUIRED**: run `cd ios && pod install --repo-update` and commit `ios/Podfile.lock` in the SAME PR, or the CI "Build iOS (no signing)" job fails (it runs vanilla `pod install` without `--repo-update`). Pin the plugin version conservatively. The chart renders the per-category segments; the `ExpenseCategory` enum (`food, travel, rent, utilities, groceries, entertainment, shopping, other`; `lib/features/expenses/domain/expense_category.dart`) already has display labels + Material icons but **no colour map** — a category->colour token map must be added (designer-owned; SCR-06 calls it "OBTCategoryChip colour mapping", but `OBTCategoryChip` is not yet extracted — `expense_category_grid.dart` inlines category UI). Keep the chart accessible (semantic summary of each segment's category + amount + percentage; never colour-only).

- **Top-N categories + "Other" bucket, and the empty/zero state (PM + designer decision).** SCR-06 does NOT define a top-N or an "Other" bucket. RECOMMEND: show all 8 categories that have non-zero spend (the enum is small), or collapse the long tail into "Other" if the designer prefers a cleaner donut — the PM/designer ratify. The empty state (no expenses this month) shows a friendly "No spending yet this month" card, NOT the chart. Loading reuses the dashboard skeleton; the error state reuses the FR-PR-05 `ContactSupportController` path like the FR-HD-01/02 error state (#62).

- **Telemetry (PII-free) — NOT yet pre-declared.** Unlike FR-AU-09, there are **no pre-declared FR-HD-03 events** in `docs/design/07-technical/telemetry-plan.md` (the Home section lists only the six `home_*` events). This PR must **declare** the new event(s) in telemetry-plan section 1.x AND wire them. RECOMMEND a single `home_spending_breakdown_viewed` (parameter-free, or a non-identifying `category_count` int) — confirm with the PM. The `uid`, any `friendshipId`, raw amounts, and category-level rupee values must NEVER be event parameters (SRS line 308). If a per-category identifier is ever logged, it is a non-PII enum name only.

- **No new Cloud Function, no rules change expected.** FR-HD-03 is a client-side read + aggregation over existing `friendships/{fid}/expenses` documents the caller already has read access to. No `simplifiedBalances` involvement (Invariant 2 N/A — this reads `expenses`, not balances). A new `firestore.indexes.json` composite index MAY be needed for the per-friendship current-month query (`where('deleted', isEqualTo: false).where('date', isGreaterThanOrEqualTo: monthStart).orderBy('date')`) — the architect confirms whether the existing `expenses` collectionGroup index (`deleted ASC + date DESC`) covers the per-friendship query or a new single-collection index is required; if so, add it and DEPLOY rules/indexes before the client (Schema Change handoff).

ESCALATION (architect decides at kickoff):

- **Read path: friendship fan-out vs a denormalised monthly-rollup.** Fan-out is the simplest (no schema change, reuses `friendsListProvider`) but issues N reads (one per friendship) and re-aggregates on every dashboard view. A denormalised per-user monthly-spend rollup (maintained by a Cloud Function trigger on expense writes) would be cheaper to read but is a much larger change and a new server writer. RECOMMEND fan-out for v1.0; file the rollup as a FUTURE optimisation issue if the architect deems the read cost material.
- **Charting library + the colour-token map.** `fl_chart` vs a hand-rolled `CustomPainter` donut (no plugin, no Podfile.lock churn, but more code + a11y work). RECOMMEND `fl_chart`; the architect ratifies the plugin (and accepts the `ios/Podfile.lock` change), and the designer owns the 8-category colour map (dark-mode + WCAG AA contrast).
- **"This Month" boundary.** Confirm the month window is computed in IST (SRS section 5.9; `date` fields are stored as Firestore Timestamps) so the boundary matches the rest of the app's date rendering (`DateFormat('dd MMM yyyy')`, no locale arg).

Story points: **5-8** (architect's call): 2 — the cross-friendship current-month aggregation read path + provider (fan-out, the user's per-category `sharePaise` sum, group axis stubbed); 1 — the charting plugin + `ios/Podfile.lock` + the category colour-token map; 1 — the breakdown card UI (chart + legend + total) + loading/empty/error states; 1 — the new telemetry event (declared + wired) + the placeholder-card swap + README/home-feature docs; 1 — widget tests (chart renders, empty/zero state, a11y summary) + provider unit tests (aggregation correctness, current-month filter, user-share-not-total, multi-friendship fold) + a boundary contract over the new files; 1 — any new `firestore.indexes.json` index + ADR-0017 + the SCR-06 / telemetry-plan doc updates.

## 5. Cross-cutting dependencies and risks

- **The aggregation semantics are the highest-risk correctness surface.** "Spend" = the signed-in user's OWN `sharePaise` from each expense's `splits`, for the current month, by category — NOT the full `amountPaise` (which includes the other member's share). A naive sum of `amountPaise` would over-report. The provider unit tests MUST assert: (a) the user's share is summed, not the total; (b) only the current month is included (an expense dated last month is excluded); (c) deleted expenses are excluded; (d) multiple friendships fold into one per-category total; (e) a category with zero spend is absent (or zero) and the chart/empty-state handles it.
- **`ios/Podfile.lock` is load-bearing.** Adding `fl_chart` (or any plugin) bumps the iOS pods. Run `cd ios && pod install --repo-update` and commit `ios/Podfile.lock` in the same PR — CI Build iOS runs `pod install` WITHOUT `--repo-update` and will fail "CocoaPods could not find compatible versions" otherwise. Also pin the plugin carefully and run `flutter build ios --no-codesign` locally if possible (the `device_info_plus` 12.3.0 episode shows a plugin can break the iOS build on a newer SDK selector).
- **The cross-friendship read cost.** Fan-out issues one expenses query per friendship. For a user with many friends this is N reads on every dashboard view. Mitigate with a sensible per-friendship `limit` is NOT correct here (a limit would drop older same-month expenses) — instead bound by the month `where('date', '>=', monthStart)`. If the architect deems the cost material, file a FUTURE denormalised-rollup issue (do NOT build it here).
- **Group axis is Sprint 3 (data-layer only).** Group expenses are out of scope; aggregate the friendship axis fully and stub/forward-compat the group axis (a comment + an ADR note), exactly as `topBalancesProvider` did. Do NOT build the Groups epic.
- **Category colour-token map is a designer dependency.** The 8-category palette must be dark-mode-safe and WCAG AA; the chart must never rely on colour alone (a11y: each segment announces "category, ₹amount, percentage"). If the designer tracks the palette separately, that is a companion design issue (§0).
- **No new Flutter dependency beyond the chart plugin.** `cloud_firestore` (reads), Riverpod, the formatter, and `friendsListProvider` are all in place. The ONLY new dependency is the chart plugin.
