## 1. Scope — what we build

FR-PR-02 (SRS section 4.2, line 175, **P1**): the user shall be able to change their phone number via an OTP re-verification flow. Entry point is the Profile / Edit Profile surface (SCR-26). Today `lib/features/profile/presentation/edit_profile_screen.dart` (lines 140-161) renders the phone field **read-only** with the helper text "Phone number cannot be changed from here." — that dead-end is what FR-PR-02 replaces. **There is no screen spec for this flow** — SCR-26 Open Question #1 (`docs/design/06-screen-specs/23-28-settle-activity-profile.md` line 521) explicitly left it unresolved ("Should the Edit Profile screen include a disabled 'Change Phone Number' row…"). Resolving that Open Question is part of this PR.

RECOMMENDED scope (ship this):

- **Reuse the auth phone-entry + OTP-entry flow, do not fork it.** `phoneEntryControllerProvider` (`lib/features/auth/application/phone_entry_controller.dart` — `+91` locked, 10-digit validation, builds `+91${digits}` at line 108) and `otpEntryControllerProvider` + `otp_entry_screen.dart` already exist for FR-AU-01..05. FR-PR-02 drives the SAME +91 validation and 6-digit OTP UI from a profile-scoped change-phone flow. Reuse the validation and OTP widgets; do NOT duplicate the +91 rule or re-implement OTP entry.

- **New repository method: `updatePhoneNumber`, NOT sign-in.** The existing `PhoneAuthRepository.verifyOtp` (`phone_auth_repository.dart:135-154`) calls `_auth.signInWithCredential(...)` — that signs a user IN and is WRONG for a phone change. Add an `updatePhoneNumber({verificationId, code})` method that builds `PhoneAuthProvider.credential(verificationId, smsCode)` and calls `_auth.currentUser!.updatePhoneNumber(credential)` (the mutate-current-user path), returning a `Result<…, AuthError>`. Map the new-number-already-taken case to the existing `AuthError.credentialInUse` (`'credential-already-in-use'` is already in `_mapException`, `phone_auth_repository.dart:211`).

- **Handle `requires-recent-login` — this is load-bearing, not an edge case.** Because FR-AU-07 persists the session and auto-logs-in, the signed-in user's last authentication will usually be older than Firebase's ~5-minute "recent login" window, so `updatePhoneNumber` will throw `requires-recent-login` for the MAJORITY of users. `requires-recent-login` is NOT currently mapped (`_mapException` falls through to `AuthError.unknown`). The architect must design the re-authentication path: the canonical phone-auth approach is to **verify the user's CURRENT number first** (`reauthenticateWithCredential(PhoneAuthCredential)`) and then proceed to the new number — i.e. a two-OTP flow (current number to re-auth, new number to update). Add a `requiresRecentLogin` `AuthError` (or equivalent) with British-English copy. Do not ship a flow that silently fails for already-logged-in users.

- **Firestore `phoneNumber` sync requires a SECURITY-RULES CHANGE (architect-owned).** `users/{userId}.phoneNumber` is currently IMMUTABLE on update: `firestore.rules` `isValidUserUpdate()` line 80 asserts `data.phoneNumber == prev.phoneNumber`, and `UserRepository.updateProfile` (`user_repository.dart:80-96`) does not write it (the `updateNotificationPrefs` doc-comment at lines 108-111 states the rules forbid client `phoneNumber` writes). The architect relaxes the rule to permit the change ONLY to the freshly-verified auth phone, e.g. `(data.phoneNumber == prev.phoneNumber || data.phoneNumber == request.auth.token.phone_number)`, keeping every other immutability/shape check intact (ADR-0010 affectedKeys pattern). Functions Dev writes the corresponding `functions/test/firestore-rules/users-update.test.ts` cases (allow change-to-token-phone; reject change-to-arbitrary-phone; reject changing other immutable fields). Token-refresh ordering is critical: after `updatePhoneNumber` succeeds, force `currentUser.getIdToken(true)` so `request.auth.token.phone_number` reflects the NEW number BEFORE the Firestore `phoneNumber` write, or the relaxed rule rejects the write against a stale token.

- **Entry point + UI.** Replace the Edit Profile read-only "cannot be changed" dead-end with a "Change Phone Number" affordance (resolve SCR-26 Open Question #1: a row/button on Edit Profile or Profile). Drive the change-phone flow; on success update the displayed number (the `authStateNotifierProvider` / `users` doc round-trip) and show the standard success snackbar.

- **Telemetry (PII-free).** Add phone-change funnel events (e.g. `phone_change_started`, `phone_change_otp_requested`, `phone_change_completed`, `phone_change_failed` with an `error_code` enum). **The phone number itself must NEVER be a parameter** (SRS line 308; the signup `phone_number_submitted` event logs only a timestamp, `01-05-auth-and-profile-setup.md` line 280). Pre-declare the events in `docs/design/07-technical/telemetry-plan.md`.

- **No money rendering.** FR-PR-02 has no monetary surface — Invariant 1 is N/A here. Do NOT add balances.

ESCALATION (architect decides at kickoff):

- **Re-auth UX shape.** Full proactive two-OTP flow (verify current number, then new number) vs. reactive (`updatePhoneNumber` first, catch `requires-recent-login`, then re-auth). RECOMMEND the flow that gives a working result for session-persisted users; the architect ratifies the exact state machine and whether the re-auth step is always-on or on-demand.
- **Firestore sync mechanism.** Client write gated by the relaxed rule (RECOMMENDED — consistent with ADR-0008 client-side user-doc writes) vs. a callable Cloud Function. Prefer the client write; a function is over-engineering (Firebase has no native "phone changed" trigger).
- **Designer involvement.** Whether the change-phone screens get a new SCR section or are documented as a reuse of the existing phone-entry + OTP screens with profile-scoped copy.

Story points: **5** (per `backlog.md` / the carry-forward "~5 SP"): 1 — `updatePhoneNumber` repo method + `AuthError` extension + unit tests; 1 — the change-phone controller/flow reusing phone-entry + OTP entry (incl. re-auth); 1 — the `firestore.rules` relaxation + `users-update.test.ts` rules tests + the token-refresh-then-Firestore-sync write; 1 — Edit Profile / Profile entry-point UI + success/error states + telemetry; 1 — widget/controller tests + boundary contract + the negative cases.

## 5. Cross-cutting dependencies and risks

- **Security-rules blast radius.** The `users` update rule is the most safety-critical client-writable rule in the app. Relax ONLY the `phoneNumber` immutability clause to `== request.auth.token.phone_number`; preserve `createdAt` immutability, the `hasOnly` key whitelist, the displayName/photoUrl/notificationPrefs/locale validators, and `updatedAt == request.time`. Functions Dev MUST add `users-update.test.ts` cases proving an arbitrary `phoneNumber` change is still rejected. The existing rules tests must stay green.
- **ID-token staleness.** After `updatePhoneNumber`, the local user object updates but the Firestore-rules `request.auth.token.phone_number` claim is stale until the token refreshes. Force `getIdToken(true)` after the auth update and BEFORE the `users/{uid}.phoneNumber` write, or the relaxed rule rejects the write.
- **`requires-recent-login` is the common path, not the rare one** (FR-AU-07 session persistence). The flow must handle it (re-auth), not just surface "unknown".
- **Contact-matching (ADR-0013/0014).** `phoneNumber` is the friend-discovery key. After a change, EXISTING friendships are unaffected (they are keyed by UID, not phone) — no friendship migration. The user simply becomes discoverable by the NEW number going forward. Do NOT attempt to rewrite friendship docs or lookup indexes; note the behaviour, change nothing there.
- **No new Cloud Function, Firestore collection, index, or Flutter plugin.** `firebase_auth` is already a dependency, so `updatePhoneNumber` / `reauthenticateWithCredential` add no plugin and **no `ios/Podfile.lock` change is expected.** The ONLY backend change is the `firestore.rules` relaxation (+ its tests). If the architect chooses a callable for the sync instead, that is a Functions change with its own region-pin + tests — but the client-write path is recommended precisely to avoid that.
