## 1. Scope — what we build

FR-PR-05 (SRS section 4.2, line 178) and the equivalent FR-SH-03 (line 272): the Profile screen's **"Contact Support"** action shall open the device's default mail client via a `mailto:` URL, pre-filled with the support address (read from Firebase Remote Config) and a diagnostic body containing the user's `userId`, app version, OS version, and device model, so the user can edit before sending.

Today the action is a stub: `lib/features/profile/presentation/profile_screen.dart:339-350` renders the "Contact Support" button (accessibility label already in place at line 339-342) whose `onPressed` shows a `SnackBar('Coming soon')`. This PR replaces that stub with the real flow.

RECOMMENDED scope (ship this):

- **`url_launcher` dependency.** `url_launcher` is NOT currently a direct dependency (only `url_launcher_web` arrives transitively). Add `url_launcher` to `pubspec.yaml`. Because this is a new FlutterFire-adjacent plugin, the iOS pod graph changes — run `cd ios && pod install --repo-update` and **commit `ios/Podfile.lock` in the same PR** (the CI "Build iOS (no signing)" job runs a vanilla `pod install` and will fail on a stale lock).
- **First Firebase Remote Config consumer.** `firebase_remote_config` (`^6.4.0`) is in `pubspec.yaml` but has ZERO usages in `lib/` today — this PR is the first client consumer (ADR-0006, `.github/shared/decision-log.md` line 188). Read the `support_email` parameter from Remote Config with an in-app default so the address works offline / before first fetch. The architect specifies the parameter key, the committed in-app default, and the fetch-and-activate timing (app-start vs lazy on tap).
- **Support service + mailto builder.** Add a small `SupportService` (or `ContactSupportController`) under `lib/features/profile/` that (a) resolves the support address from Remote Config, (b) assembles the diagnostic body (`userId`, app version, OS version, device model), (c) percent-encodes subject + body, and (d) launches the `mailto:` URI via `url_launcher` (`launchUrl(..., mode: LaunchMode.externalApplication)`).
- **Diagnostic context.** The body needs app version + OS version + device model. The architect decides the source: `package_info_plus` (app version) and `device_info_plus` (device model) are the conventional plugins but are NOT yet dependencies — adding them widens the pod graph again. A lighter alternative is `dart:io Platform.operatingSystem` / `operatingSystemVersion` for OS and a build-time app-version constant, deferring device-model precision. Architect's call at kickoff; whatever is chosen, the same `Podfile.lock` rule applies if a plugin is added.
- **Telemetry.** Emit `support_email_opened` on successful launch (this event is already pre-declared in the SRS analytics funnel list, section 5.10). The payload carries NO PII — no `userId`, email, or device identifiers as analytics parameters (the `userId` belongs only in the mailto body the user sees, never in telemetry). Follow the existing per-feature telemetry-constants pattern (e.g. `settlement_history_telemetry.dart`).

ESCALATION (architect bundles or defers at kickoff):

- **FR-SH-04 no-mail-client fallback (P1, line 273-274).** If `canLaunchUrl(mailto)` is false (no mail client configured), show a fallback dialog displaying the support email with a "Copy" button (clipboard). RECOMMENDED bundle — it is ~0.5 SP, shares the same service, and FR-SH-04 is the natural completion of FR-PR-05. If bundled, story points rise from ~2 to ~3.
- **Ripping out the other Profile "Coming soon" stubs** (Delete Account at `profile_screen.dart:263/292`, etc.) — OUT OF SCOPE; those map to FR-AU-09 (P1) and are separate stories.

Story points: **2-3** (1 — `SupportService` + Remote Config read + mailto builder + `support_email_opened` telemetry + unit tests with a fake launcher/Remote Config; 1 — `profile_screen.dart` wiring replacing the snackbar stub + widget tests asserting the button builds the correct mailto URI and the fallback path on `canLaunchUrl == false`; +1 if FR-SH-04 fallback dialog is bundled).
