## 1. Scope — what we build

**The AC-11 "Open Settings" deep-link CTA.** When a user has denied (or permanently denied) an OS permission, the app should offer a button that deep-links straight to the app's OS settings page so they can re-enable it. Two surfaces currently fall short of that because no Flutter plugin capable of opening the OS settings screen is in the lockfile:

1. **Notifications / SCR-27 (FR-AC-04 / FR-PR-03, AC-11).** `lib/features/profile/presentation/notification_preferences_screen.dart` renders `_OsPermissionBanner` (line 337) when `NotificationPermissionController` reports `denied`/`permanentlyDenied`. Per PR #55 architect §2.4 the banner shipped **WITHOUT** the "Open Settings" button, because `firebase_messaging` does not expose `openAppNotificationSettings()` on the Dart API. **Verified at this kickoff: still absent in the installed `firebase_messaging-16.3.0`** (grep of the package `lib/` finds no `openAppNotificationSettings`/`openAppSettings`). The banner copy ("Notifications are turned off for this app. Enable them in your device settings to receive alerts.") ships, but the actionable button does not.
2. **Friends contact-permission / SCR-10 (FR-FR-01).** `PermissionDeniedView` (`lib/features/friends/presentation/widgets/permission_denied_view.dart`) renders an "Open Settings" `FilledButton` when contact permission is `deniedPermanently`; its `onOpenSettings` (wired in `add_friend_screen.dart:279,291`) calls `ContactService.openSettings()`, which today calls `FlutterContacts.openExternalPick()` — a contact-picker fallback, NOT the app's OS settings page. The source carries an explicit TODO (`contact_service.dart:77`: "In production, consider using app_settings or similar for navigating directly to the app permission settings page").

Current state (read it; do not re-derive):
   - `lib/features/profile/presentation/notification_preferences_screen.dart` — `_OsPermissionBanner` (text-only today); `_isPermissionBlocked` gates it on `PermissionState.denied || permanentlyDenied`.
   - `lib/features/notifications/application/notification_permission_controller.dart` — the `PermissionState` enum (`...denied`, `permanentlyDenied`) and the in-memory `wasPermanentlyDenied` flag (the cross-launch-persistence `shared_preferences` follow-up is SEPARATE — do NOT bundle it).
   - `lib/features/friends/presentation/widgets/permission_denied_view.dart` + `lib/features/friends/data/contact_service.dart` (`openSettings()` -> `FlutterContacts.openExternalPick()`) + `lib/features/friends/application/contact_permission_controller.dart` (the `openSettings()` notifier method) + `add_friend_screen.dart:275-297`.
   - `lib/core/services/url_launcher_service.dart` (FR-PR-05) — the precedent for a thin `lib/core/services/` platform-binding shim behind a provider, faked in tests via a Riverpod override. The new settings service should mirror it exactly.
   - `pubspec.yaml` — `firebase_messaging: ^16.2.0` (resolved 16.3.0), `url_launcher: ^6.3.2`; NO `app_settings`, `permission_handler`, or `shared_preferences`.

RECOMMENDED scope (ship this):

   - **Add ONE native settings-deep-link plugin and a thin core service.** Add `app_settings` (RECOMMENDED — a tiny, purpose-built package whose `AppSettings.openAppSettings(type: AppSettingsType.notification | AppSettingsType.settings)` opens the OS settings screen; lighter than `permission_handler`) behind a new `lib/core/services/app_settings_service.dart` (`AppSettingsService` + `appSettingsServiceProvider`), mirroring `UrlLauncherService`. The service exposes e.g. `openNotificationSettings()` and `openAppSettings()` so both call sites bind to a fakeable seam, never to the plugin directly.
   - **Wire the notifications banner CTA (AC-11).** Add an "Open Settings" button to `_OsPermissionBanner` that calls `appSettingsServiceProvider`'s notification-settings open. The banner copy is unchanged; the button is the graceful-degradation extension the §2.4 fallback ladder promised.
   - **Wire the friends contact-permission CTA (close the `openExternalPick` gap).** Replace `ContactService.openSettings()`'s `FlutterContacts.openExternalPick()` with the shared `AppSettingsService.openAppSettings()` so the permanently-denied "Open Settings" button deep-links to the real OS app-settings page; remove the `contact_service.dart:77` TODO. Keep the non-permanent `denied` path's "Grant Permission" re-request unchanged.
   - **iOS `Podfile.lock` MUST change.** `app_settings`/`permission_handler` are native plugins, so adding one bumps `ios/Podfile.lock`. Run `cd ios && pod install --repo-update` and **commit `ios/Podfile.lock` in the same PR** — the CI "Build iOS (no signing)" job runs `pod install` WITHOUT `--repo-update` and fails with "CocoaPods could not find compatible versions" otherwise. Add the Android `<queries>`/manifest entry if the chosen plugin requires one (mirror the FR-PR-05 `mailto` `<queries>` precedent).
   - **No Cloud Function, no rules/index/schema change.** Pure client + dependency chore. Invariants 1 and 2 are N/A (no money, no `simplifiedBalances`); Invariant 3 is N/A (opening OS settings is not sharing — do NOT route it through the share sheet).
