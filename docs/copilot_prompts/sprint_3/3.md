STANDING CAVEATS (read first)
────────────────────────────────────────

- **The four invariants are untouched and re-affirmed.** (1) Money is integer paise — `OBTAmountInput`'s paise logic and `onChanged(int paise)` contract, and the `formatInrFromPaise()` boundary in `OBTAmountInput` / `OBTActivityRow` / `OBTSettleUpCard`, are **unchanged**; amounts render via `OBTText.amount` (Bricolage tabular) but **no `paise / 100`** is introduced. (2) `OBTSettleUpCard` continues to **read** the `simplifiedBalances` projection only and shows the **single** pre-filled suggested payment — never a who-paid-whom graph. (3) OS system share sheet only. (4) Single Firebase project; pre-merge testing on the Emulator Suite. Any item that weakens one is a blocking defect — refuse and cite the invariant.
- **`onPrimary` is INK, never white.** The FAB reskin is the canonical case: `backgroundColor` `secondary` → **`primary`** marigold; `foregroundColor` `Colors.white` → **`onPrimary` ink**. White on marigold measures ≈ 2.5:1 (fails WCAG 2.1 AA); a white-on-marigold glyph is a defect that the DC-01 contrast gate already rejects.
- **Scope is the six widgets ONLY — token/type reskin, no structural change.** No layout change, no new control, no new state, no widget added or removed. Do **not** convert any screen and do **not** build any new Haldi component (that is DC-03). The **optional** enhancements flagged in §4.1 are **deferred — do not do them here**: the `OBTBottomNav` → Material 3 `NavigationBar` active-pill migration (a structural change) and the `OBTFloatingActionButton` press-spring. A diff that alters layout, the paise contract, or the formatter **fails review** (DC-02 AC #3 negative case).
- **No hard-coded Haldi hex at the widget call sites.** All colour via `Theme.of(context).colorScheme` / `OBTColors`; all type via `theme.textTheme` / `OBTText`; all radii via the `AppTheme` scale. (Guardable by grep: no `Color(0xFF…)` Haldi literal inside the six widgets.) `theme.dart` remains the single source of truth.
- **Lockstep test updates must be intentional and traceable.** The `OBTFloatingActionButton` test currently asserts `backgroundColor == secondary` and `foregroundColor == Colors.white`; under Haldi these become `primary` (marigold) and `onPrimary` (ink) — change those assertions deliberately, traceable to §1.2 / §4.1 (§D item 13). **Keep every structural assertion (child count, finders, layout, semantics, the `onChanged(int paise)` tests) UNCHANGED** to prove no structure moved while the token assertions prove the new skin (§A.5).
- **Tooling + lessons carried from DC-01:**
  - fvm-pinned: `fvm flutter analyze lib test`, `fvm flutter test`, `dart format .` (CI gates on `dart format --set-exit-if-changed .`). Commit with `fvm exec git commit`, push with `fvm exec git push` (bare `dart`/`flutter` fail under the fvm SDK in the lefthook hooks).
  - **`google_fonts` in tests.** To assert the new tokens, the widget tests should pump under `theme: AppTheme.light` / `AppTheme.dark`, which builds `google_fonts`. Keep those in `testWidgets` (the test zone absorbs the runtime font fetch). Do **not** add a pure `test()` that builds `AppTheme` — it leaks the fetch ("There is no current invoker"). If a non-widget assertion needs the resolved theme, prime it inside a leading `testWidgets` (see the DC-01 `test/app/theme_*_test.dart` pattern).
  - If `fvm flutter analyze` surfaces **unrelated** `flutter_contacts` / `PermissionStatus` errors, the `.dart_tool/package_config.json` has drifted to a stale version — run `fvm flutter pub get` (the **pinned** SDK) to re-sync; do **not** run bare `flutter pub get` (it downgrades the lock).
  - `google_fonts` is pure-Dart and no native plugin is added → **no `ios/Podfile.lock` change** (do not run `pod install --repo-update`).
