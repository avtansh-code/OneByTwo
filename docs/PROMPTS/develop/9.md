PHASE 1 — RESOLVE THE USER-DOC CREATION DECISION
────────────────────────────────────────

Owner: architect.

This decision was deferred at PR #7. It must be resolved BEFORE implementation begins. The architect produces a new ADR at `.github/shared/decision-log.md` (next ADR number in sequence — likely ADR-0007).

Title: "User document creation: client-side write vs Cloud Function trigger."

The ADR must present both options honestly:

  **Option A — Client-side write (in the profile-setup flow):**
  - The Flutter app, after the user submits their display name and optional photo, performs a Firestore `set()` on `users/{userId}` with the typed shape from `docs/design/07-technical/firestore-schema.md`.
  - Firestore Security Rules enforce that `request.auth.uid == userId` and that the document does not already exist (creation is one-shot).
  - Pros: simpler architecture, no Cloud Function cold-start on the critical signup path, no eventual-consistency window between auth completion and user-doc availability.
  - Cons: client owns the schema for user-authored fields (acceptable given the invariants do not protect this collection); a malicious client with a valid auth token could in theory write a malformed document if rules are imperfect.

  **Option B — Cloud Function on auth.user().onCreate():**
  - A Cloud Function fires when Firebase Auth creates a new user. It writes a minimal `users/{userId}` document with `phoneNumber` and `createdAt`. The profile-setup screen then writes `displayName` and optionally `photoUrl` via a separate update.
  - Pros: server controls the schema for the "skeleton" of every user record; convention matches how `simplifiedBalances` is handled.
  - Cons: cold-start latency on the critical first-signup screen; the profile-setup screen has to handle a brief eventual-consistency window where the user doc may not yet exist; two writes instead of one; more moving parts.

The architect picks one and records the decision in the ADR. Recommended choice (state your reasoning if you disagree): **Option A**, because the user document is user-authored data, not derived/protected data. The invariants only mandate server-side writes for derived state. Adding a Cloud Function here would solve a security problem the invariants do not actually have, while introducing real latency and complexity on the critical signup path.

The ADR must close with: "Implication for PR #9: …" specifying which screen writes the document, which Firestore rule changes are required, and which integration test paths verify it.
