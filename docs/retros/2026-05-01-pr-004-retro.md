## What worked well

1. **Test-first discipline was honoured.** Commit 1 wrote red tests for the validator,
   formatter, and screen before any implementation code existed. Commits 2-4 made them
   green in order (formatter+validator, controller, screen). This produced a clean
   audit trail and caught the `5XXXXXXXXX` invalid-prefix case early.

2. **Feature-first folder structure proved correct.** Every file landed exactly where
   the skeleton prescribed. No folder restructuring or ad-hoc path decisions were
   needed. The test mirror at `test/features/auth/` matched naturally.

3. **Dependency pinning in PR #3 paid off.** PR #4 added zero new dependencies. Every
   package needed (Riverpod, Firebase Analytics, etc.) was already available, avoiding
   `pubspec.yaml` churn.

4. **Analytics abstraction.** The `AnalyticsService` interface with a
   `FirebaseAnalyticsService` production implementation and fake for tests was a clean
   pattern. Tests run without Firebase initialisation, and the real implementation is
   injected via a Riverpod provider override. This should be the standard pattern.

5. **PR description was thorough.** The four-invariant checklist was ticked with
   rationale. The file table with line counts and test coverage made review efficient.
   The "Next PR" pointer at the end provided continuity.

6. **CI pipeline caught real issues.** The Flutter Lint and Test job ran in 67 seconds
   and the full suite (including iOS build) completed in under 18 minutes. No flakes
   on the final push.

## What was friction

1. **CI/platform fixups consumed half the commits.** Commits 6-12 (7 out of 12) were
   platform project updates (Android build.gradle, CocoaPods), Firebase init
   revert, CI config file restoration, and FlutterFire CLI installation. The actual
   feature work was 5 commits. This indicates the skeleton did not fully anticipate
   Firebase-dependent builds.

2. **Firebase initialisation ping-pong.** Commit 9 added `Firebase.initializeApp()`,
   commit 10 reverted it because `firebase_options.dart` is gitignored. The app
   currently runs without Firebase initialisation, meaning the analytics provider
   would crash at runtime. This remains unresolved.

3. **One commit violated Conventional Commits.** Commit 7 ("Add CocoaPods integration
   and update project configuration") has no type prefix. The pre-commit hook or CI
   should catch this. It slipped through because the squash-merge message was corrected
   at PR level.

4. **Commit 5 is unclear.** "feat(auth): add phone-number entry screen implementation
   with validation and telemetry" duplicates the intent of commits 2-4. It appears to
   be a catch-all commit that should have been squashed during development, not shipped
   as a separate commit in the PR.

5. **No controller unit tests.** `PhoneEntryController` is tested only through the
   widget test (`phone_entry_screen_test.dart`). A dedicated unit test file
   (`phone_entry_controller_test.dart`) would test the state transitions and analytics
   firing in isolation, independent of the widget tree.

## Hooks and invariants

- **PreToolUse hooks did not fire** during PR #4 development because no invariant
  violations were attempted. This means we have zero data on true-positive or
  false-positive rates from this PR.
- **PostToolUse `dart-format.sh`** presumably fired on Dart file edits but produces
  no logged output — there is no audit trail of hook activity.
- **No hook logging mechanism exists.** We cannot verify after the fact whether hooks
  ran, what they checked, or what they allowed/blocked. This is a gap — hooks should
  log their decisions (at minimum: file path checked, result) to a session log file.

  hooks only match `Edit|Write` tool uses, not commit message formatting. Consider
  adding a commit-message lint hook (lefthook already supports `commit-msg`).

## Patterns to lock in

1. **Analytics abstraction pattern.** Abstract `AnalyticsService` interface, production
   `FirebaseAnalyticsService` implementation, Riverpod provider with test override.
   Location: `lib/features/<feature>/application/analytics_provider.dart`.

2. **Test file naming and location.** Mirror the source path:
   `lib/features/auth/presentation/widgets/india_phone_input_formatter.dart` is tested
   by `test/features/auth/india_phone_input_formatter_test.dart`. Test files drop the
   intermediate directory segments but keep the feature prefix.

3. **Validator in `lib/core/`.** Validators that are feature-agnostic (e.g., Indian
   mobile number validation) live in `lib/core/validators.dart`. Feature-specific
   validators live in the feature's `application/` folder.

4. **PR description shape.** The PR #4 description is the template: Description,
   References, SRS Requirements, Type of Change, Invariant Checklist (with rationale),
   Testing, Quality, Telemetry, Documentation, Files Added/Modified table, Manual Smoke
   Test, "Next PR" pointer.

5. **TDD commit rhythm.** Commit 1: red tests. Commits 2-N: implementations that turn
   tests green. Final commits: integration wiring and smoke test updates.

6. **`FakeAnalyticsService` pattern for widget tests.** Override the provider in
   `ProviderScope.overrides` to inject a fake that records logged events. Assert against
   `fakeAnalytics.loggedEvents` after interactions.
